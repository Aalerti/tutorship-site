# Backend plan

## Цель

Сделать сайт, где первокурсник заходит без регистрации и сразу смотрит конспекты, гайды и ссылки, а тьюторы через закрытую админскую часть могут добавлять, редактировать и удалять материалы на доске.

Главная идея: публичная часть остаётся простой и быстрой, а управление контентом переносится в backend с базой данных, авторизацией и ролями.

## Роли

### Гость

Обычный первокурсник.

Что может:

- открыть сайт без регистрации;
- выбрать направление: ПИ, ФИИТ, МОАИС, САУ, КБ, ИВТ;
- смотреть карточки гайдов;
- открывать конспекты, ссылки и прикреплённые файлы;
- фильтровать материалы по семестру, типу и направлению.

Что не может:

- добавлять материалы;
- редактировать материалы;
- удалять материалы;
- видеть админские кнопки управления.

### Тьютор

Авторизованный пользователь.

Что может:

- войти в админскую часть;
- добавить новый конспект или гайд;
- изменить название, описание, дату, направление, семестр, статус и ссылки;
- загрузить или заменить файл;
- удалить материал;
- скрыть материал без удаления;
- видеть список своих материалов.

### Администратор

Главный управляющий сайтом.

Что может:

- всё, что может тьютор;
- создавать и отключать аккаунты тьюторов;
- назначать роли;
- удалять чужие материалы;
- восстанавливать скрытые материалы;
- смотреть журнал действий.

## Предлагаемый стек

### Backend

Рекомендуемый вариант: Node.js + Fastify или NestJS.

Для этого проекта лучше начать с Fastify, потому что он проще, легче и быстрее поднимается. NestJS можно взять, если хочется сразу строгую архитектуру с модулями, сервисами и DI.

Минимальный стек:

- Node.js;
- TypeScript;
- Fastify;
- Prisma ORM;
- PostgreSQL;
- JWT access token;
- refresh token через httpOnly cookie;
- Zod для валидации входных данных.

### Database

PostgreSQL.

Почему:

- нормальная реляционная структура;
- удобно хранить направления, семестры, материалы, пользователей и роли;
- легко делать фильтры;
- хорошо работает с Prisma.

### Хранение файлов

На первом этапе можно хранить не сами файлы, а ссылки:

- Google Drive;
- Yandex Disk;
- GitHub releases;
- внешние PDF-ссылки;
- ссылки на страницы с конспектами.

На втором этапе можно добавить загрузку файлов:

- локальное хранилище на сервере;
- S3-compatible storage;
- Cloudflare R2;
- Yandex Object Storage.

Для продакшена лучше сразу думать про S3/R2, чтобы не потерять файлы при переезде сервера.

## Структура данных

### User

Пользователь админской части.

Поля:

- `id`;
- `email`;
- `passwordHash`;
- `name`;
- `role`: `admin` или `tutor`;
- `isActive`;
- `createdAt`;
- `updatedAt`.

Пароли хранить только в виде хеша. Для хеширования использовать argon2 или bcrypt.

### Direction

Направление обучения.

Поля:

- `id`;
- `slug`: `pi`, `fiit`, `moais`, `sau`, `kb`, `ivt`;
- `shortName`: `ПИ`, `ФИИТ`, `МОАИС`, `САУ`, `КБ`, `ИВТ`;
- `fullName`;
- `description`;
- `isActive`;
- `sortOrder`.

### Semester

Семестр или учебный блок.

Поля:

- `id`;
- `number`;
- `title`;
- `description`;
- `sortOrder`.

### Material

Основная сущность: конспект, гайд, подборка ссылок или материал к экзамену.

Поля:

- `id`;
- `title`;
- `slug`;
- `description`;
- `content`;
- `type`: `guide`, `notes`, `exam`, `links`, `other`;
- `directionId`;
- `semesterId`;
- `authorId`;
- `coverImageUrl`;
- `externalUrl`;
- `fileUrl`;
- `publishedAt`;
- `createdAt`;
- `updatedAt`;
- `isPublished`;
- `isPinned`;
- `sortOrder`.

Логика:

- если `isPublished = false`, материал виден только тьюторам и админам;
- если `isPinned = true`, карточка поднимается выше остальных;
- `externalUrl` нужен для ссылок на Google Drive, GitHub, Notion и другие внешние источники;
- `fileUrl` нужен для загруженного PDF или архива;
- `content` можно использовать для короткого описания или полноценной страницы материала.

### MaterialAttachment

Дополнительные вложения к материалу.

Поля:

- `id`;
- `materialId`;
- `title`;
- `url`;
- `kind`: `pdf`, `doc`, `image`, `archive`, `link`, `other`;
- `sortOrder`;
- `createdAt`.

### AuditLog

Журнал действий.

Поля:

- `id`;
- `userId`;
- `action`;
- `entityType`;
- `entityId`;
- `before`;
- `after`;
- `createdAt`.

Нужен, чтобы понимать, кто удалил или изменил материал.

## API

### Публичные endpoints

Эти ручки доступны без авторизации.

`GET /api/directions`

Возвращает список направлений.

`GET /api/materials`

Параметры:

- `direction`;
- `semester`;
- `type`;
- `search`;
- `limit`;
- `offset`.

Возвращает только опубликованные материалы.

`GET /api/materials/:slug`

Возвращает один опубликованный материал.

`GET /api/semesters`

Возвращает список семестров.

### Auth endpoints

`POST /api/auth/login`

Принимает:

- `email`;
- `password`.

Возвращает access token и ставит refresh token в httpOnly cookie.

`POST /api/auth/refresh`

Обновляет access token.

`POST /api/auth/logout`

Удаляет refresh cookie.

`GET /api/auth/me`

Возвращает текущего пользователя.

### Admin endpoints

Все ручки ниже требуют авторизации.

`POST /api/admin/materials`

Создать материал.

`PATCH /api/admin/materials/:id`

Изменить материал.

`DELETE /api/admin/materials/:id`

Удалить материал.

Лучше на первом этапе делать soft delete:

- `deletedAt`;
- `deletedBy`.

Так будет проще восстановить случайно удалённый конспект.

`POST /api/admin/materials/:id/publish`

Опубликовать материал.

`POST /api/admin/materials/:id/unpublish`

Скрыть материал.

`POST /api/admin/uploads`

Загрузить файл.

`GET /api/admin/users`

Список тьюторов. Только для администратора.

`POST /api/admin/users`

Создать тьютора. Только для администратора.

`PATCH /api/admin/users/:id`

Изменить пользователя. Только для администратора.

`POST /api/admin/users/:id/disable`

Отключить пользователя. Только для администратора.

## Админская часть

Админку лучше сделать отдельным разделом:

`/admin`

Страницы:

- `/admin/login`;
- `/admin/materials`;
- `/admin/materials/new`;
- `/admin/materials/:id/edit`;
- `/admin/users`;
- `/admin/settings`.

На доске для тьюторов можно показывать управляющие кнопки только после входа:

- добавить материал;
- редактировать карточку;
- удалить карточку;
- скрыть карточку;
- закрепить карточку.

Для гостя этих кнопок быть не должно вообще.

## Frontend-интеграция

Текущий сайт можно не выбрасывать.

Переход лучше сделать в несколько этапов:

1. Оставить текущий Hugo-дизайн как визуальную основу.
2. Добавить backend и API.
3. Сделать отдельную админку.
4. На главной странице заменить статические карточки гайдов на данные из `GET /api/materials`.
5. Для направлений использовать `GET /api/directions`.
6. Для страниц материалов использовать `GET /api/materials/:slug`.

Если Hugo станет мешать, можно позже перенести frontend на Vite + React или Next.js. Но для первого backend-этапа не обязательно сразу переписывать весь сайт.

## Авторизация и безопасность

Нужно обязательно сделать:

- пароли только в хешированном виде;
- refresh token в httpOnly cookie;
- access token короткоживущий;
- rate limit на login;
- проверку ролей на admin endpoints;
- валидацию всех входных данных;
- CORS только для домена сайта;
- защиту загрузки файлов по типу и размеру;
- ограничение размера изображений и PDF;
- журнал действий для удаления и публикации.

На первом этапе можно не делать регистрацию. Аккаунты тьюторов создаёт администратор.

## Удаление материалов

Удаление лучше сделать в два шага:

1. Тьютор нажимает удалить.
2. Материал получает `deletedAt`, исчезает с публичной доски, но остаётся в базе.

Администратор может:

- восстановить материал;
- удалить окончательно.

Это защитит от случайных удалений.

## Публикация материалов

Новые материалы можно создавать как черновики.

Статусы:

- `draft`;
- `published`;
- `hidden`;
- `deleted`.

Первый простой вариант:

- тьютор создаёт материал;
- материал сразу становится опубликованным.

Более аккуратный вариант:

- тьютор создаёт черновик;
- администратор публикует.

Для вашего сайта, скорее всего, сначала хватит прямой публикации тьюторами.

## Миграция текущих данных

Нужно пройтись по текущим markdown-файлам и перенести их в базу.

План:

1. Найти все текущие гайды в `content/posts`.
2. Вытащить из front matter:
   - заголовок;
   - дату;
   - описание;
   - ссылку;
   - семестр;
   - направление.
3. Создать seed-скрипт Prisma.
4. Заполнить таблицы `Direction`, `Semester`, `Material`.
5. Проверить, что публичная доска показывает те же карточки, что сейчас.

## Этапы реализации

### Этап 1. Скелет backend

- создать папку `backend`;
- настроить TypeScript;
- поднять Fastify;
- добавить healthcheck `GET /api/health`;
- настроить `.env`;
- подключить Prisma;
- подключить PostgreSQL.

Результат: backend запускается локально и отвечает `ok`.

### Этап 2. База данных

- описать Prisma schema;
- создать таблицы:
  - users;
  - directions;
  - semesters;
  - materials;
  - material_attachments;
  - audit_logs;
- сделать миграцию;
- написать seed для направлений и семестров.

Результат: база готова хранить материалы.

### Этап 3. Публичное API

- `GET /api/directions`;
- `GET /api/semesters`;
- `GET /api/materials`;
- `GET /api/materials/:slug`;
- фильтры по направлению, семестру и типу.

Результат: сайт может получать карточки из backend без логина.

### Этап 4. Авторизация тьюторов

- login;
- refresh;
- logout;
- me;
- хеширование паролей;
- middleware проверки токена;
- middleware проверки роли.

Результат: тьюторы могут войти, гости не имеют доступа к управлению.

### Этап 5. CRUD материалов

- создать материал;
- изменить материал;
- скрыть материал;
- удалить материал через soft delete;
- закрепить материал;
- записывать действия в audit log.

Результат: тьюторы могут управлять доской.

### Этап 6. Админка

- страница входа;
- список материалов;
- форма создания;
- форма редактирования;
- кнопки публикации, скрытия и удаления;
- список пользователей для администратора.

Результат: контент можно менять без ручного редактирования markdown.

### Этап 7. Подключение текущего дизайна

- заменить статические карточки на загрузку из `GET /api/materials`;
- показывать админские кнопки только после входа;
- добавить состояния загрузки и ошибки;
- сохранить текущую визуальную концепцию доски.

Результат: публичный сайт выглядит как сейчас, но данные приходят из backend.

### Этап 8. Загрузка файлов

- endpoint загрузки;
- проверка размера;
- проверка расширения;
- сохранение файла;
- привязка файла к материалу.

Результат: тьюторы могут прикладывать PDF, архивы и изображения.

### Этап 9. Деплой

- выбрать хостинг backend;
- настроить PostgreSQL;
- настроить переменные окружения;
- настроить CORS;
- настроить домен;
- включить HTTPS;
- настроить backup базы.

Результат: сайт работает не только локально.

## Что лучше сделать первым

Первым делом нужно не трогать дизайн, а сделать минимальный backend:

1. `GET /api/health`;
2. PostgreSQL + Prisma;
3. таблица `materials`;
4. `GET /api/materials`;
5. `POST /api/auth/login`;
6. `POST /api/admin/materials`.

После этого уже можно подключать доску к живым данным.

## Риски

- Если сразу переписать весь frontend, можно надолго сломать уже собранный дизайн.
- Если хранить файлы только локально на сервере, их можно потерять при переносе.
- Если не сделать soft delete, случайное удаление материала будет больно откатывать.
- Если не сделать роли, любой тьютор сможет управлять всем без ограничений.
- Если не сделать audit log, будет сложно понять, кто что изменил.

## Рекомендуемый MVP

MVP должен включать:

- публичный список материалов;
- фильтр по направлению;
- фильтр по семестру;
- логин для тьюторов;
- создание материала;
- редактирование материала;
- скрытие материала;
- soft delete;
- seed направлений;
- seed семестров;
- один админский аккаунт.

После MVP можно добавлять:

- загрузку файлов;
- журнал действий в интерфейсе;
- красивую админку;
- права на конкретные направления;
- черновики и модерацию;
- поиск по содержимому.
